The normal day-to-day workflow

  1. Edit generate_template.yaml in the pypsa-india project root, choosing an unused scenario name.
  2. Run snakemake generate_template.
  3. Fill the new Excel workbook and edit the scenario_config.yaml generated beside it.
  4. Set run.scenario in base_config.yaml to that folder name.
  5. Run snakemake run, then read the validation report, solve log and, when policies are configured, the constraint audit.
Keep the project root in view. It is the folder containing Snakefile, base_config.yaml, generate_template.yaml, scripts/ and data/. Run every command in this guide from that folder unless a step says otherwise.
02 · The model in plain language

What is the model deciding?

At every modelled time step, demand must be supplied. The model chooses generation, storage use and flows between connected locations. In expansion mode it can also choose how much permitted new capacity to build. It minimizes the cost represented by the workbook while satisfying the configured limits.

TermPicture it asExample
ScenarioOne complete set of study assumptions.data/all_india/ contains its workbook and YAML.
BusA location or connection point where electricity balances.KL for Kerala; NR for the northern regional grid.
LoadDemand attached to a bus, changing over time.A KL load with 10 MW in every hour.
GeneratorAn asset that supplies electricity.An existing 20 MW unit, or a candidate solar plant.
Carrier / technologyA carrier groups assets; a technology identifies a type of candidate/cost assumption.Technology Solar_PV_Utility, carrier Solar.
ConstraintA rule the result must satisfy.An annual CO₂ ceiling or a minimum renewable share.

Power is not energy

MW measures power at an instant. MWh measures energy over a duration. A 10 MW generator running for 3 hours supplies 30 MWh. A 20 MW storage unit with max_hours: 4 has 80 MWh of energy capacity.

Two independent choices

SettingChoiceWhat changes?
familydispatchOperate fixed capacity. Nominal capacity is frozen at the larger of nominal and minimum capacity.
familyexpansionAllow extendable components to add capacity within their bounds; new storage components are extendable by default.
modemyopicSolve one model year, carry capacity forward, then solve the next year.
modeperfect_foresightOptimize the configured investment periods together in one network.

Start with a one-year dispatch model. Add expansion, more locations and more policies after you can explain the simple result.

How workbook rows become model components

Workbook inputModel componentImportant behavior
GeneratorsGeneratorExisting capacity is fixed. The carrier named Market is the exception: it is extendable before dispatch-mode capacity freezing.
New_GeneratorsGenerator vintageOne candidate vintage is created for each model year. Pipeline_p_min and Pipeline_p_max set that vintage’s MW bounds.
New_Storage.Type: StoreStoreThe decision is energy capacity, e_nom, in MWh. Pipeline_storage is an MWh minimum for this type.
New_Storage.Type: StorageStorageUnitThe decision is power capacity, p_nom, in MW. Energy is determined by storage.max_hours; Pipeline_storage is an MW minimum.
LinksLinkCreates the explicit connection and its MW bounds, efficiency and costs.
Transfer_CapacityTwo fixed directional LinksFor each corridor/year capacity, the workflow creates one nonnegative Link in each direction. This is available corridor capacity, not an accumulating investment vintage.

In family: dispatch, generator, Link and StorageUnit power capacities and Store energy capacities are fixed at the larger of their nominal and minimum values. In family: expansion, candidate Generators and explicit Links can grow when their extendable field is true. New Store and StorageUnit rows are created as extendable capacities; their pipeline values set minimum capacity.

03 · One-time setup

Set up your computer.

These instructions use Windows PowerShell. You need the complete project folder, Python 3.13, and internet access for the first dependency installation. Install the dependencies before running the workflow commands below.

  1. Open PowerShell in the project folder

    In File Explorer, open pypsa-india, click the address bar, type powershell and press Enter. Or use Set-Location with your actual path:

    Set-Location 'C:\path\to\pypsa-india'
Get-Location
Test-Path .\Snakefile
py -3.13 --version

    Test-Path should print True. If it prints False, change to the folder containing Snakefile before continuing.

  2. Create a project Python environment

    py -3.13 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt

    A virtual environment keeps this project's dependencies together. Reuse it; you do not need to recreate it for each scenario.

    PowerShell refuses to activate the environment

    Use its executables directly. This avoids changing your computer's execution policy:

    .\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\snakemake.exe --version

    For later commands, replace python with .\.venv\Scripts\python.exe and snakemake with .\.venv\Scripts\snakemake.exe.

  3. Check the installation

    python --version
snakemake --version
python -c "import pypsa; print(pypsa.__version__)"
snakemake run -n --config scenario=er

    The last command is a dry run: it lists planned jobs without solving them. It needs the shipped er scenario and its workbook. If your project copy does not include those inputs, use your own filled scenario after creating it.

When you open a new terminal tomorrow

Set-Location 'C:\path\to\pypsa-india'
.\.venv\Scripts\Activate.ps1
The default solver is HiGHS. The pinned requirements include highspy. Gurobi, CPLEX and GLPK require separate installation; commercial solvers also require the appropriate license. Start with HiGHS unless your study already specifies another solver.
Dependencies and optional installation checks

The project pins PyPSA 1.2.4, Snakemake 9.23.1, HiGHS 1.14.0, Linopy 0.8.0, pandas 2.2.3, NumPy 2.2.1, openpyxl 3.1.5, PyYAML 6.0.3, matplotlib 3.10.0, netCDF4 1.7.2 and pytest 9.0.3. Use requirements.txt as the installation source.

python -m pytest tests -q
python tests/test_roundtrip.py

These checks exercise implementation behavior, including a synthetic template-to-solve example. They do not validate the forecasts in your own workbook.

04 · Reuse existing inputs

Run a scenario that is already filled.

A scenario name is its folder name under data/. Check that it has scenario_config.yaml and the intended workbook. Choose the scenario explicitly on your first run so you know what will execute.

snakemake run -n --config scenario=er
snakemake validate_inputs --config scenario=er
Get-Content .\results\er\validation_report.txt
snakemake run --config scenario=er

Read the validation report before interpreting a solve. Errors must be fixed. Warnings describe assumptions or suspicious inputs that still need review.

Shipped scenarioPurpose / inputWhat to expect
erEastern regional grid, one bus per state.The smallest shipped scenario and the quickest end-to-end check.
all_indiaNational workbook with five regional electricity buses.Inspect scenario.years and the numeric snapshots.resolution before running. Peak-week sampling reduces the model size; the national case remains larger than the tutorial.
nr, wr, sr, er, nerRegional scenarios with their own workbooks.Read each scenario's configuration and input assumptions before running.

Make one scenario the default

Edit the existing run section of base_config.yaml; do not add a second run block:

run:
  scenario: er
snakemake run

The optional --config scenario=NAME override wins over this default for that command.

05 · Your own study

Create the workbook and scenario together.

FileEdit it when…It controls…

  1. Save a copy of your current template settings

    Keep them if they describe another study. Edit the root generate_template.yaml, choose a new folder-safe name, and set your geography, years and carriers. The next section provides a complete small example.

  2. Generate the pair

    snakemake generate_template
    data/
  beginner_demo/
    beginner_demo_template.xlsx
    scenario_config.yaml

    The default workbook name ends in _template.xlsx; template.output can choose another filename. This command generates structure and placeholders. It does not download demand forecasts or populate a real fleet.

  3. Fill and configure

    Follow the Excel rules. Replace placeholders with your data, save and close Excel, and edit the companion scenario YAML for execution. Later changes to generate_template.yaml do not automatically edit an existing scenario.

  4. Validate, preview and run

    snakemake validate_inputs --config scenario=beginner_demo
snakemake run -n --config scenario=beginner_demo
snakemake run --config scenario=beginner_demo

    For the shortest ongoing command, set run.scenario: beginner_demo in base_config.yaml and use snakemake run.

The workbook already exists: choose a safe regeneration method

Ordinary generation stops when it would overwrite an existing workbook or companion config. An unused scenario name is simplest for a new study.

template:
  merge: true
  # force: true

Use only one option. merge retains existing rows in retained columns and adds new structure; inspect all resulting sheets and new placeholders. Existing scenario YAML values take precedence during a merge, so a root-template edit alone may not change an existing setting. force replaces the pair after backups; use it only when replacement is intended. A workbook backup uses the .xlsx.bak suffix.

A merge can preserve formerly selected sheets as well. It is not a substitute for reviewing the workbook after a schema change. Keep your own dated copy before a substantial edit.

06 · A worked example

Build a model you can check by hand.

This synthetic teaching example has one electricity bus in Kerala, one load and one existing generator. Its numbers are chosen for easy checking; they are not estimates of Kerala's demand or generating costs.

Prefer to run first? Download the filled workbook and scenario YAML, then run them using the download instructions. Continue below to learn how to generate and fill the same example yourself.

A. Generate the teaching template

Save your current root template settings elsewhere, then use the following complete generate_template.yaml. If beginner_demo already exists, use another unused name in both scenario.name and template.output.

scenario:
  name: beginner_demo
  currency: INR
  fiscal_year: true
  years: [2030]
mode: myopic
family: dispatch
spatial:
  boundary: {level: state, id: KL}
  resolution: state
  external: none
  role_buses: shared

  select: all
  resolution: 24

  new_generators: false
  new_stores: false
  storage_units: false
  links: false
  transfer: false

snakemake generate_template

Open data/beginner_demo/beginner_demo.xlsx. This example deliberately names the workbook beginner_demo.xlsx; without template.output, the default name would end in _template.xlsx. Keep the generated companion YAML beside it.

B. Fill the hourly sheets

The workbook still needs a full 8,760-hour input year. resolution: 24 selects one snapshot every 24 hours later; it does not make the input sheets 365 rows long.

This enters values, not formulas. Repeat on the appropriate sheet. The generated hourly sheets are empty below their headers and units. You must create the counters and timestamps as well as the demand/profile values.
Create the missing counter and timestamp columns in Excel
  1. On Demand_KL, type 1 into A3 and =A3+1 into A4. Select A4:A8762 with the Name Box and press Ctrl+D to fill the formula down. Copy A3:A8762 and use Paste Special → Values in the same range. The last counter must be 8,760.
  2. On P_max_pu, enter 1 April 2029 00:00 into A3 as an Excel date/time, not text. In A4 enter =A3+1/24. Select A4:A8762 and press Ctrl+D. Format the column as yyyy-mm-dd hh:mm; verify that A8762 is 2030-03-31 23:00. Then copy the whole range and Paste Special → Values.

E. Save, validate and run

Save the workbook and close Excel. Check that scenario_config.yaml points to beginner_demo.xlsx and still has the intended settings.

snakemake validate_inputs --config scenario=beginner_demo
Get-Content .\results\beginner_demo\validation_report.txt
snakemake run --config scenario=beginner_demo

The one-bus workbook may emit two generic warnings about absent Storage/Store role buses. For this specific example that is expected: both storage components and their links are disabled. There should be no validation errors.

Check your answer. The expected result uses 365 snapshots × 24 hours, with 10 MW generation at each snapshot, 87,600 MWh annual generation and load, and an objective of 262,800,000 INR. A successful solve enforces bus balance within solver tolerance. The cost is 10 × 8760 × 3000. The CO₂ factor is deliberately zero for this synthetic example.

Inspect results/beginner_demo/csvs/2030/generation.csv, objective.csv and capacity.csv. Policy audit/config CSVs contain headers but no data rows because constraints: [] applies no policy in this myopic example. Storage, Link and renewable-curtailment charts are not applicable to this topology/carrier set.

Try a controlled change

Change every demand value from 10 to 12 MW, save, validate and run again. The fixed 20 MW unit can still supply it; expected annual generation becomes 12 × 8760 = 105,120 MWh, and variable cost becomes 315,360,000 INR. This is a hand-calculated exercise. Demand above the available 20 MW has no feasible supply in this one-generator model; an infeasible solve is then the expected result.

07 · Input discipline

Follow the workbook's structure.

RowPurposeWhat to do
1Column headersKeep the names and spelling generated by the template.
2Units / typesKeep this row. It is not an asset or an hour of data.
3 onwardYour input dataFill required values; remove unused placeholder data rows in asset/lookup sheets.
  1. Replace every Please fill here. It is an invalid placeholder. A required field left blank inside a real row is also an error.
  2. Use exact identifiers. A generator's bus must match Buses.name. A load named Factory_A needs Demand_Factory_A. Carrier spelling must agree across the YAML and workbook.
  3. Keep hourly rows chronological. Do not sort a demand column by size or paste the selected daily/three-hour samples into a full-hour input sheet. Missing internal hours are not trailing padding.
  4. Keep keys unique. Give each asset its own name. Candidate technology/bus pairs and corridor endpoint pairs must be consistent with their lookup rows.
  5. Use numeric values in the stated units. Writing Unit=Crore/MW does not automatically convert a value to rupees. Convert inputs before entering them.
  6. Save evaluated values. For calculated Excel inputs, recalculate and save in Excel, or paste the final numbers as values. The Python loader does not run Excel's formula engine.
  7. Save and close Excel before regeneration. An open workbook may be locked on Windows.

09 · Settings without Python edits

Read and edit YAML confidently.

  years: [2030, 2035, 2040]     # Unique, increasing integers
  fiscal_year: true            # FY2030 ends in March 2030
mode: myopic
family: expansion
snapshots:
  select: peak_weeks
  resolution: 3               # Hours between selected snapshots
components:
  new_generators: true
  new_stores: false
  links: true
constraints: []               # No additional policy constraints yet

Select the workbook explicitly

paths:
  workbook: my_model_template.xlsx

A basename looks beside the scenario YAML. Relative paths are searched from the scenario folder, then project root, then current working directory; an absolute path is also supported. Without a configured path, the folder must contain exactly one usable .xlsx. Excel lock files beginning ~$ and backup files are ignored.

For paired generation, template.output must be an .xlsx directly inside data/<scenario.name>/. That keeps workbook and YAML together.

Solver options

solver:
  name: highs
  options:
    threads: 2
    presolve: "on"
  highs:
    solver: ipm

A matching nested block such as solver.highs overrides matching entries in solver.options. If you switch solver, replace incompatible options rather than carrying HiGHS option names into Gurobi. Snakemake's core allowance and a solver's thread setting are related resource choices, but are not the same setting.

Perfect-foresight period weights
mode: perfect_foresight
investment_periods:
  years: {2030: 5, 2035: 5, 2040: 1}
  discount_rate: 0.02

Durations are positive whole years. An omitted duration defaults to the gap to the next model year; the last period defaults to one year. The social discount rate is separate from technology WACC. A joint multi-period objective is a whole-horizon quantity and is not the cost of every individual year.

10 · Time matters

Supply hourly data; choose sampling separately.

By default, the label FY2030 means 1 April 2029 through 31 March 2030. With scenario.fiscal_year: false, 2030 means January through December 2030. A complete hourly source has 8,760 values for a non-leap year or 8,784 when it includes 29 February. A complete 8,760-value source is also accepted for a leap-year target through the calendar mapping described below; the validator requires at least 8,760 values.

snapshots.selectBehaviorWhen useful
allStart with the full year, then retain every resolution-th hour.A simple initial run; resolution 1 preserves the hourly chronology.
custom_daysUse the month/day rows in Custom days, then apply the resolution.A deliberately selected representative-day study.
peak_weeksFor each calendar month, group coincident demand across all active loads by ISO year/week and choose the group with the largest demand sum. Retain the chosen whole week, clipped to the financial year, then subsample.A smaller study emphasizing higher-demand weeks under this selection rule.
snapshots:
  select: peak_weeks
  resolution: 3
“Peak weeks” has a specific meaning here. It selects a large weekly demand sum, not necessarily the week containing the single highest hourly peak. Three-hour thinning can also omit a particular peak hour. Reserve and other snapshot-dependent policies see the selected snapshots.

Three sets of time weights

  • Generator weights annualize generation, energy and emissions accounting to 8,760 hours.
  • Storage weights track sampled elapsed hours. Storage does not simulate the omitted weeks of a peak-week run.
  • Myopic objective weights retain sampled elapsed hours, with capital-cost scaling for the sample. Perfect-foresight objectives additionally use annualized operating and investment-period weights.

Consequently, representative sampling is a modelling choice, not proof that the result equals a full hourly study. Compare scenarios using the same time selection and accounting assumptions.

Leap years, shorter profiles and ragged tails

Demand year columns are read independently, so a shorter non-leap column can sit beside a longer leap-year column with trailing padding. Full profiles are aligned to the target fiscal/calendar year; missing 29 February values can be copied from 28 February. Availability profiles are reused seasonally across planning years. Keep all profile rows in time order; timestamp text is not a substitute for correct ordering.

For example, a leap-year demand column with 8,783 values retains the first 8,760 as a complete non-leap source year, drops 23 trailing values with a warning and maps 29 February from 28 February. This preserves the chosen input convention; it does not recover an unknown missing original observation.

One load or several?

By default, the template creates one load per electricity bus, including EXT when present. You can instead request names:

loads: [City_A, Industry_A]

The generator creates Demand_City_A and Demand_Industry_A. Fill each load's bus in Loads if the load name does not itself match a bus. Multiple loads may attach to the same bus. Keep names unique and at most 24 characters so the Demand_ sheet prefix fits Excel's 31-character limit.

Geographic policy scope

scope: {bus: NR} selects assets stamped with that bus. State/region scopes use state_id/region_id metadata. Use a scope represented by the actual network. A state-specific policy cannot recover state-level assets from an aggregated bus whose components do not carry that state assignment.

A configuration edit does not relocate workbook rows. After changing boundary, resolution or role-bus settings, regenerate deliberately or edit the workbook's bus/asset connections to match, then validate. Existing filled bus names remain actual inputs.
12 · Extend a study

Add a technology with all its inputs.

A new carrier label does not create a generator. A technology needs an asset row, availability, costs and capacity bounds appropriate to its component type.

Example: a new utility-solar candidate at NR

Use technology Solar_PV_Utility, carrier Solar and bus NR. This example assumes NR already exists and your scenario includes the years you want to model.

  1. Ensure Solar is in the complete scenario carriers list. If the carrier is new, add its CO2 row and an optional plot colour. An absent factor is treated as zero with a warning, so supply a truthful factor even when zero is your intended assumption.
  2. Enable components.new_generators: true. Create the required sheets using the template/merge workflow. When merging, edit the existing scenario settings too: existing YAML values win over template defaults.
  3. Add a New_Generators row: TECHNOLOGY=Solar_PV_Utility, bus=NR, carrier=Solar, Type=Generator, p_nom_extendable=TRUE.
  4. Add matching Pipeline_p_min and Pipeline_p_max rows for every model year. For example, 0 and 100 mean the model may build up to 100 new MW in that vintage.
  5. Fill matching Capital_cost, Lifetime, FOM, Fuel_cost and Startupcost rows, using the actual economic assumptions and units. A missing lookup may produce an unintended default, so inspect built costs as well as validation messages.
  6. Provide an hourly Solar availability column in P_max_pu; use a zero P_min_pu unless a forced minimum is truly intended.
  7. Add Solar to a policy's eligible_carriers only if it should count toward that policy. The carrier list and the eligible-policy list serve different purposes.
  8. Validate, build or run, then check Solar's optimal capacity and generation in the result tables.

Adding an existing unit instead

Use Generators with a unique name, existing MW, marginal cost, commissioning year and lifetime. The current builder treats existing non-Market units as fixed; setting their p_nom_extendable cell to TRUE does not turn them into normal candidate builds. Use New_Generators for expansion.

Adding a model year

Update scenario.years, every selected wide-year sheet, demand columns, and every year-keyed policy map. Retained old assets carry forward while active; candidate pipeline bounds create another vintage. Perfect-foresight scenarios also need a review of investment-period durations.

Cost intuition

Candidate capital cost is annualized using a capital recovery factor based on WACC and lifetime; FOM is added when enabled. Representative-time studies scale this annual cost consistently with the sampled objective. Existing generation reads its own all-in marginal cost; new generation reads the Fuel_cost assumptions. The workbook's Unit text is informational, so keep the numeric basis consistent before running.

Carrier names carry accounting meaning

Use the same carrier spelling in scenario settings, asset rows, availability profiles and the CO2 table. A carrier groups assets for profiles, reporting and policy selection. TECHNOLOGY identifies the candidate and its cost/lifetime lookup rows.

In the standard workbook workflow, the CO2 table is tonnes CO2 per electrical-output MWh. Use basis: electrical_output for CO2 policies. FuelSupplyLimit can separately use fuel_input, which divides generator output by efficiency. Renewable-share policies count the selected eligible Generator carriers against served load in scope; they do not infer external certificates or unmodelled procurement.

Curtailment charts recognize Solar, Wind and Hydro ROR carriers. Other carriers can appear in generation tables without receiving a renewable-curtailment chart. Choose names consistently rather than relying on an arbitrary new label to acquire a built-in interpretation.

13 · Storage and connections

Distinguish power, energy and wiring.

New_Storage.TypePyPSA componentPipeline unitThink about
StorageStorageUnitMWCharging/discharging power, energy duration via max_hours, efficiency and state of charge.
StoreStoreMWhEnergy capacity and the Links that provide charging/discharging paths and power capability.

components.new_stores and components.storage_units are aliases selecting the same New_Storage sheet. They do not filter rows by Type. The row's Type chooses the component.

The storage: block below sets StorageUnit defaults only. It creates no assets by itself. Enable the component, fill New_Storage and Pipeline_storage, and provide the connection Links needed by your chosen buses.

storage:
  max_hours: 6
  standing_loss: 0.002

standing_loss is an hourly fractional energy loss. Select values from your technology assumptions; the examples here are not technology recommendations.

Two ways to connect buses

  • Explicit Links: use Links for your chosen topology, capacity bounds, costs and efficiencies. Fixed dispatch studies need positive nominal/minimum capacity wherever a Link is necessary for supply.
  • Annual transfer corridors: use Transfer_Capacity for a total available corridor MW in each year. The builder makes one nonnegative directional Link each way. A corridor policy restricts an existing path; it does not create that path.

When charging and discharging Links are added

A storage asset on an electricity bus connects there directly. For an asset on a store or storage role bus, the builder can add two nonnegative Links: charging and discharging. It does so only when there is no existing Link in either direction between that role bus and its selected electricity hub. Supplying one explicit Link prevents automatic creation of the pair; check both directions yourself.

These automatically added Links have unit efficiency and extendable power capacity. A BUS_Store or BUS_Storage name selects the corresponding electricity bus when it exists; otherwise the builder uses its hub bus. In a dispatch study, zero nominal/minimum Link capacity remains zero after freezing, so provide usable explicit capacity. Model actual losses, costs and geography deliberately in the workbook.

Local storage needs local connections

role_buses: shared can connect several regional grids through one storage/store bus. Electricity can then pass between regions through that shared node, even without being stored. For regional locality, use role_buses: per_bus and fill the corresponding local storage and Link rows. Inspect actual workbook connections, not only the YAML label.

Direction matters for lossy Links. PyPSA applies p1 = -efficiency × p0. With efficiency below 1 and negative allowed p0, reverse flow can appear to gain energy. For physical losses in both directions, use two nonnegative directional Links with intended capacities/costs, or the generated Transfer_Capacity pair.
14 · Policy rules

Add one constraint, then check its audit.

Policies belong in the scenario YAML under one constraints list. Each needs a supported class and a unique, nonblank name. Start with one rule so you can understand how it changes the result.

constraints:
  - class: CO2EmissionLimit
    name: co2_cap
    limit_tco2: 12000000
    basis: electrical_output

All policy values in this chapter illustrate syntax. They are not calibrated targets for your study or additions to the synthetic tutorial.

Scalars, year maps and scope

A scalar applies in each modelled year. A year map must cover every modelled year; missing targets are not interpolated. For example, with years 2030 and 2035:

limit_tco2: {2030: 12000000, 2035: 10000000}
scope: {region_id: SR}

Omit scope for the whole model, or select {bus: NR}, {state_id: KL} or {region_id: SR} where supported. ImportExportLimit instead names endpoints and does not accept geographic scope. A scope cannot create missing assets.

1. CO2EmissionLimit — cap annual emissions

Required: name, limit_tco2, basis. The limit is finite and nonnegative, in tonnes of CO₂. The class accepts electrical_output or fuel_input, but this workbook builder declares CO2 factors on an electrical-output basis. Use basis: electrical_output here. Fuel-input CO2 accounting requires a separately prepared network with matching declared factor metadata and valid efficiencies; changing only this YAML field is rejected. FuelSupplyLimit can use its own fuel-input accounting independently.

- class: CO2EmissionLimit
  name: co2_cap
  limit_tco2: 12000000
  basis: electrical_output
2. FuelSupplyLimit — cap carrier energy or fuel

Required: name, carrier, limit_mwh, basis. The limit is finite and nonnegative. Use electrical_output for electrical energy or fuel_input for input energy. The carrier and scope must be valid. If no matching generator exists in a horizon, the policy is recorded as inapplicable for that horizon.

- class: FuelSupplyLimit
  name: coal_budget
  carrier: Coal
  limit_mwh: 90000000
  basis: fuel_input
  scope: {region_id: NR}
3. RPOConstraint — require renewable generation share

Required: name, target_share in (0, 1], and nonempty eligible_carriers. Eligible generation must cover the required fraction of served load in scope. Eligible carriers must be configured; only matching Generator output counts. An empty eligible-generator set is an error for this policy. Its served-load denominator must be positive. served_load is the supported accounting basis.

- class: RPOConstraint
  name: renewable_share
  target_share: 0.43
  eligible_carriers: [Solar, Wind, Hydro]
  scope: {state_id: KL}
  accounting_basis: served_load

43% is 0.43, not 43. Negative Load values are not accepted by this policy's load accounting.

4. MonthlyCufsProfile — bound monthly utilisation

Required: name, carrier and at least one nonempty maximum/minimum month map. Keys are calendar months 1–12; values lie in [0,1]. Unlisted months have no bound. The denominator includes total built capacity, including new capacity.

- class: MonthlyCufsProfile
  name: hydro_monthly
  carrier: Hydro
  max_cf_by_month: {6: 0.30, 7: 0.35, 8: 0.35, 9: 0.30}
  scope: {region_id: SR}

A positive minimum forces output. Variable-renewable minima are refused unless you deliberately set allow_variable_renewable_min: true. A month map is not a year map.

5. ImportExportLimit — restrict an existing corridor

Required: name, different existing from_bus/to_bus, and at least one export/import limit. Limits are nonnegative MW. When a Link or Line connects the endpoints, the policy limits their combined signed net sending-end flow; alternate paths remain possible. If the buses exist but no direct connection is present in a horizon, the policy is recorded as inapplicable for that horizon.

- class: ImportExportLimit
  name: nr_wr_exchange
  from_bus: NR
  to_bus: WR
  max_export_mw: 5000
  max_import_mw: 5000
6. TechnologyPhaseOut — cap a whole generator fleet

Required: name, carrier. Write max_capacity_mw explicitly; omission defaults to zero. This caps existing plus new matching generation. It does not retire fixed assets to make an impossible ceiling feasible.

- class: TechnologyPhaseOut
  name: coal_phaseout
  carrier: Coal
  max_capacity_mw: {2030: 10000, 2035: 5000, 2040: 0}

Ensure those are exactly your model years and that fixed surviving capacity is compatible with the ceiling.

7. ReserveMargin — require firm generation capacity

Required: name, margin as a nonnegative ratio. Credited capacity must cover the highest selected coincident load plus the margin. Explicit capacity_credit_by_carrier values lie in [0,1]. For omitted credits, the model averages p_max_pu over the peak_hours highest-demand snapshots (default 1); this averaging does not change the peak-load requirement. Generators with carrier exactly unserved_energy receive no credit.

- class: ReserveMargin
  name: planning_reserve
  margin: 0.15
  scope: {region_id: WR}
  capacity_credit_by_carrier: {Solar: 0.25, Wind: 0.15}

Optional settings can add profile averaging and storage credit:

  peak_hours: 20
  storage_peak_duration_h: 4

These are illustrative assumptions, not recommended study parameters. peak_hours counts selected snapshots; at three-hour sampling, 20 means 20 samples. Storage receives credit only when storage_peak_duration_h is set. StorageUnit power is limited by min(1, max_hours / duration); Store energy contributes at most e_nom / duration. Storage on the same bus is pooled, with touching Link ratings used as a delivery ceiling where present. Inspect those paths and their power limits before using this approximation.

There is no separate transmission/import-capacity credit. Imported supply represented as a normal Generator is treated according to its carrier and availability. Review the selected snapshots before treating this as an annual peak adequacy test; this deterministic margin does not calculate probabilistic reliability.

8. StoreCyclingLimit — limit discharge throughput

Required: name, nonnegative max_cycles. This works on Store components, not StorageUnits. Windows are daily, weekly, monthly or annual. It limits discharge energy relative to each Store's energy capacity.

- class: StoreCyclingLimit
  name: battery_daily_cycles
  max_cycles: 1.0
  window: daily
  carrier: Battery Storage
  scope: {region_id: NR}
  max_snapshot_hours: 1.0

The default requires near-hourly sampling. Increasing the permitted interval can hide within-window cycles; do so only with that interpretation understood. It is not suitable for the 24-hour beginner tutorial.

Policy class names. Use the eight class names listed in this chapter. Each generated scenario includes a commented catalogue. python scripts/make_scenario_config.py --all refreshes catalogue comments; it does not generate or fill a workbook.

Resources, interruption and reruns

The bundled default profile supplies one Snakemake core, so plain commands work. --cores 4 allows more workflow jobs to use resources; solver thread settings are a separate choice in the solver options. Avoid launching multiple large solves merely to speed up a study.

To stop a run you started in the current terminal, press Ctrl+C and let it stop. Fix the reported problem, then repeat the original command. If Snakemake explicitly reports incomplete output, use --rerun-incomplete. Check for another active run before dealing with a directory lock.

Nothing to be done means the requested outputs are up to date according to Snakemake's dependency records. It is not a new validation or solve. Saved changes to declared inputs normally trigger the affected downstream jobs. Do not delete .snakemake as a routine troubleshooting step.

Understand validation messages before solving

snakemake validate_inputs checks workbook structure, required values, bus and carrier references, profile lengths, topology and constraint configuration. Errors stop the workflow; warnings leave a decision or an assumption for you to review.

  • Extra year columns and sheets outside the active registry are ignored with a warning.
  • A carrier absent from the CO2 table receives a zero emissions factor with a warning. Add an explicit, appropriate factor before interpreting emissions.
  • Profiles need a complete hourly source year. A complete year followed by an incomplete tail can be retained with a warning; missing or nonnumeric values inside the retained source are errors.

Validation cannot decide whether a demand forecast, fuel price, plant lifetime or topology is a good representation of your study. Check those assumptions against your own sources.

Check the tables before the charts.

Check whether a policy actually applies

A valid policy can have no matching assets in a horizon: a fleet may have retired, a region may have no relevant storage, or two existing buses may have no connecting corridor. The constraint audit records such cases with applicable=false and a not applicable explanation. Its placeholder passed=true is neither evidence of compliance nor a policy failure. Read the explanation and decide whether the missing application matches the study you intended.

Unknown carrier or endpoint names, invalid scopes and malformed limits are configuration errors. Applicable audit rows that fail stop the solve workflow. A policy restricts represented assets; it does not create them.

How to read constraint_audit.csv

A policy may create several rows: per year, month, Store or other applicable scope. lhs is the realized left-hand quantity, rhs the permitted bound and sense the comparison.

  • For <=, a positive margin means the result is below the ceiling: rhs − lhs.
  • For >=, a positive margin means the result is above the floor: lhs − rhs.
  • The audit uses 1e-6 + 1e-12 × max(abs(lhs), abs(rhs)) as a scale-aware numerical tolerance in the row's native unit. A tiny negative margin can still pass within that tolerance.

Check the audit's applicability and number of rows, not just the final passed value. A policy on the wrong scope can answer the wrong question while remaining mathematically valid.

The solver says infeasible

No solution satisfies all represented requirements at once. Use the workbook and the policy audit configuration to check these in order:

  1. Can supply reach each load? A disconnected load bus cannot use generation elsewhere.
  2. Is enough supply available in every selected hour? Check installed/candidate limits, availability, retirement and corridor capacity.
  3. Do forced minimums conflict? Must-run generation, monthly minimum CUFs and storage restrictions can prevent balance at low demand.
  4. Are policies mutually achievable? A tight CO₂/fuel ceiling, high RPO share or reserve margin may require assets the model is not allowed to build.
  5. Are the units right? MW versus MWh, ratios versus percentages and currency errors can change a bound by factors of 1,000 or more.

Use a copied scenario to isolate a suspected policy or topology change, then record the difference. Removing a policy can diagnose infeasibility; it does not validate the original policy case.

The solver says unbounded, or the answer looks physically surprising

Check extendable capacities with missing upper bounds, negative costs and energy-gaining connection cycles. In particular, a lossy Link used with negative flow can create the reverse-direction issue described in storage and connections. An optimal solver status does not establish that the topology represents the physical system you intended.

What to include when asking a colleague for help

Share the scenario name, exact command, Python/PyPSA/Snakemake versions, the first specific error, validation_report.txt, the failing rule's log, scenario YAML and the smallest workbook that reproduces the issue. State what you expected and what changed since the last successful run. Include the configured solver and its termination status.

Words you will see in the project.

TermMeaning here
Annualization / annuityConverting an upfront capital cost into an annual capacity cost using a lifetime and financing rate.
Availability / p_max_puThe fraction of nominal generator power available in a time step. A 20 MW generator at 0.5 can produce at most 10 MW.
BrownfieldCapacity carried from an earlier solve into a later model year, subject to the retirement logic.
Candidate / vintageAn asset option the expansion model may build; its vintage identifies its build year.
Capacity factor / CUFEnergy divided by nominal power times the relevant hours. A monthly CUF bound constrains energy across that month.
CarrierA named group such as Solar, Wind or Coal, used to match profiles, costs, emissions and policies.
DAG / ruleSnakemake's dependency graph / one workflow task. Dependencies determine the job order.
DispatchHow much power an asset supplies or absorbs at each snapshot.
Extendable / p_nom_optA capacity the optimization may choose / its solved power capacity. Check the bounds and family setting.
Fiscal yearIn this project, FY2030 runs from 1 April 2029 through 31 March 2030.
Marginal costCost per additional MWh generated, separate from capacity cost.
Myopic / perfect foresightSequential year-by-year optimization / joint multi-period optimization.
NetCDF / .ncThe file format used to save built and solved PyPSA networks.
ObjectiveThe cost expression the optimizer minimizes, given the constraints and weighting.
ScopeThe buses, states or regions whose matching assets a policy applies to.
Snapshot / weightA modelled time step / the hours or weighting it represents in an equation.
SolverThe optimization engine, such as HiGHS, called after PyPSA constructs the mathematical problem.
Store / StorageUnitAn energy reservoir with separate connections / a storage component with power rating and max_hours.
Validation / dry-runInput structure and data checks / a preview of jobs without executing them.
WACCWeighted average cost of capital: the financing rate used in annualized investment costs. Enter a fraction such as 0.08 for 8%.
YAMLThe text format for configuration. Indentation is meaningful; use spaces and keep the generated key structure.

The short version.

New study

  1. Edit root generate_template.yaml.
  2. Generate the input pair.
  3. Fill the workbook.
  4. Edit its scenario YAML.
  5. Validate, run and review.

Existing study

  1. Open its data/NAME/ folder.
  2. Check workbook and YAML.
  3. Select run.scenario.
  4. Preview with -n.
  5. Run and inspect results.

Before sharing

  1. Explain warnings.
  2. Confirm optimal status.
  3. Inspect policy rows.
  4. Reconcile tables/charts.
  5. Archive assumptions and inputs.
# Open the project and activate its existing environment.

snakemake validate_inputs --config scenario=beginner_demo

snakemake run --config scenario=beginner_demo

# Or run the scenario selected by run.scenario in base_config.yaml.
snakemake run

Three files to remember: root generate_template.yaml creates new inputs; root base_config.yaml selects a default and supplies shared settings; data/NAME/scenario_config.yaml describes that scenario. The filled workbook beside it supplies the actual data.
